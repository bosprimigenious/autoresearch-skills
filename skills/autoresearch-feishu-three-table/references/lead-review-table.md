# 组长初检表

本表记录审核角色对特定题号和特定交付版本的初检，不是把 QA 结论机械复制为状态。项目名称只用于人类识别；写入定位必须使用当期题号、论文 canonical ID 和主包摘要。

## 唯一定位

1. 从当期领题表读取题号和论文身份。
2. 从完成提交/验收表读取当前主包摘要、提交批次和 QA 引用。
3. 在组长初检表按题号查找记录，再核对精确标题/方法名和摘要。
4. 无记录、重复记录、同名异题或摘要不一致时停止，标记 `CONFLICT`。

不要只按方法简称搜索后选择第一行；公开方法名可能存在大小写、连字符或同名版本差异。

## 回填字段

按 live schema 映射并只填审核角色可写字段：

- 当前期次、权威题号和提交批次；
- 项目/方法精确名称；
- 初检状态或结论；
- 证据摘要与 QA 报告引用；
- 主包 SHA256 或 commit/release 标识；
- 静态审查、已有运行证据、未独立复跑项；
- 返修项、复验条件或待补证项；
- 审核角色、审核时间和适用协议版本。

审核人字段使用当前系统身份，不复制旧用户 ID 或姓名文本。证据引用保留私有对象别名或受控附件，不写本机路径和临时 capability URL。

## 状态决策

- 所有适用硬门槛通过、主包身份一致、必需材料齐全，且现场状态枚举存在等价“初检通过”时，才可选择通过。
- 已证实具体缺陷、证据能定位且当前审核角色决定退回时，才选择返修，并写最小修复与复验条件。
- QA 未完成、运行未复核、权限不足、产物不一致或结论存在冲突时，优先使用当前 schema 的待补证/待复核/处理中等中性状态。
- 如果 live schema 没有中性状态且用户明确要求既不标返修也不标通过，保持原状态不变，只在允许的备注/证据字段记录待补项；备注字段也不可写时不做状态 mutation。

因此，一个已完整通过 QA 的记录可以在身份与产物均核对后进入“初检通过”；另一个仍有证据缺口的记录不能因为前者通过而批量同判，也不能仅因未完成就自动标返修。

## 证据复核

回填前逐项核对：

1. 题号与当前期次一致；
2. 论文、源码 revision 与题目说明一致；
3. 主包摘要与 QA 报告审查对象一致；
4. QA 的研究质量、实现、Harbor、提交格式、隐私和证据门结论无遗漏；
5. 两条轨迹、正式结果和 Verifier/Hidden 证据对应当前包；
6. 报告明确区分静态检查、包内既有运行证据和本次未独立复跑项；
7. 返修或通过的文字不超过证据边界。

不能只看一个总绿灯。QA 报告版本旧于当前包、摘要不匹配或聚合门未全过时，初检状态不得写通过。

## 批量回填与写后检查

不同项目必须作为独立预演和写入：分别保存 before digest、拟改字段、证据和预期状态。单条写入后立刻回读，再处理下一条；禁止用一个批量成功响应替代逐条核验。

最终报告逐条说明：目标别名、题号是否核验、产物摘要是否匹配、实际修改字段、回读结果、未写字段及原因。任何一条失败不影响如实报告另一条成功，但整批结论必须写部分完成。
